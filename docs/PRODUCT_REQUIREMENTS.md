# GameArchiveManager 产品需求与验收标准

> 创建：2026-10-24。目的：让新 ChatGPT 对话、本机 Codex 和其他维护者不依赖聊天上下文即可持续开发。
> 状态说明：**已确认** = 用户已明确提出或既有交接记录已确认的要求；**拟定** = 推荐实现方案，仍需产品验收；**待验证** = 尚无足够真实测试证据。本文是需求文件，**不是功能已完成证明**。
> 当前实际功能、版本、测试与发布身份仍以 START_HERE.md、docs/CURRENT_STATUS.md、project_state.json、源码及实际测试证据为准；本文不覆盖这些文件的状态结论。

## 1. 用户目标（已确认）

GameArchiveManager 应从以解压解密为主的游戏资源处理工具，发展为**好用、美观、可靠的 Windows 游戏资源管理器**：

1. 对现有 UI 不满意，要求整体提升视觉设计、操作体验和适配性，不再只做局部补丁。
2. 密码库目前未满足需要，必须完善为真正可管理、可持久、安全、可供任务复用的功能。
3. 保留既有一键识别、递归解压和密码恢复能力。
4. 将来增加一键创建压缩包、一键加密压缩，不能只会解压。
5. 明显扩展解压解密格式覆盖率，尤其是常见、分卷、嵌套和伪装扩展名的游戏资源。
6. 保留原有数据和已通过验证的安全行为；不能为了美观、速度、格式数量损害用户文件。

## 2. 既有累计 UI 要求（已确认，来自项目交接记录）

- 首屏干净、现代、美观、易理解；不出现额外黑色控制台窗口。
- 浅色“晴空”、深色“墨台”、跟随系统三种模式，切换时背景、文字、按钮等完整同步；中文/English 切换与选择状态记忆。
- 首次在可见屏幕中央以合理尺寸打开，记住后续窗口大小、位置、显示器及最大化状态；原显示器不可用时恢复到可见区域。
- 支持窄窗、宽窗、高/矮窗、缩放及拖动：控件不重叠、不截断；布局自适应，操作不卡顿。
- 文件路径独占易读的一行；路径编辑区随窗口变宽；“浏览”和主要执行按钮大小协调。
- 标题与外观控件不要相互挤压；合理间距（既有目标约 8px），扩大窗口时多余高度主要留给任务状态而不是把表单拉散。
- 设置分类清楚，保存操作持续可见；设置与主窗口各自可独立最小化；操作提示与模态对话框不相互遮挡。
- 任务状态必须用文字说明准备、扫描、解压、验证、成功和失败原因，不能仅凭颜色表达；键盘焦点、Tab 导航可见可用。
- Android、AZ、PC 三个“忽略内容”开关相互独立、默认关闭。

**注意：**现有 Tkinter 界面虽已尝试部分要求，但并不代表用户已对视觉和实际交互验收。新版 UI 设计方案需经截图/交互验收，不能只以 UI 单元测试通过判断完成。

## 3. 新版信息架构（拟定，待视觉验收）

建议主导航：**智能解压**、**压缩加密**、**密码库**、**任务记录**、**设置**。首页应突出单次常用操作，进阶选项按需展开，避免所有设置拥挤在一起。

- 智能解压：拖入或浏览文件/目录、查看实际识别格式和范围、开始任务、查看阶段进度及最终输出。
- 压缩加密：选择文件/目录、目标格式、压缩级别、是否加密、密码来源及输出位置；显示校验结果。
- 密码库：独立列表管理，不再让“每行一个明文密码”的文本框成为唯一管理入口。
- 任务记录：当前任务、历史、阶段、失败原因、输出位置、重试/复制诊断（不泄漏秘密）。
- 设置：语言、外观、扫描和平台范围、外部工具、处理限制、安全选项；高级参数与日常操作分离。

技术选型尚未决定，不应因改 UI 就重写稳定解压核心。原有窗口位置、主题、语言与设置数据需要兼容或可安全迁移。

## 4. 密码库（第一优先级）

### 4.1 必须达到的能力

- 独立、可理解的管理界面：添加、编辑、删除、查找已有条目；列表默认遮盖密码，仅用户明确操作才临时显示或复制。
- 支持用户手工添加密码、从已成功验证的解压任务保存密码、重启后继续使用；错误密码不能误入“已验证密码”。
- 用户能够知道保存是否成功、密码库是否读取失败、任务是否实际复用了候选密码；不能把“损坏/解密失败”静默表现为空库。
- 继续使用 Windows 当前用户范围的 DPAPI 保护（现有存储），默认不落明文文件，不把密码泄漏到日志、报告、历史或含密码的完整命令行。
- 保存时采用临时文件 + 安全替换等原子写入策略，异常时尽量保留上一份有效密码库；兼容已存在的 passwords.json。
- 去重规则应明确，避免不小心把大小写不同的真实密码合并；删除和编辑应影响指定条目，不意外替换整个库。
- 正确区分“保存到本机”“本次会话记住”“自动尝试已保存密码”等语义，旧设置 save_passwords/auto_try_password 的实际接线需要核对，不得显示无效开关。

### 4.2 安全与回归验收

- 重启后仍能读取、显示为遮盖态、正确复用已保存密码；新增/编辑/删除/搜索正常。
- 重复密码、空输入、特殊 Unicode/中文和大小写不同的密码行为符合设计。
- 密码库损坏、DPAPI 解密失败、磁盘无写权限、中断写入均有明确、脱敏的错误，不误删旧库。
- 任何失败报告、历史、屏幕默认状态及自动测试输出均不出现秘密明文；密码被复制后的剪贴板安全策略需后续明确。
- GUI 测试与实际 Windows 用户环境测试均要通过；自动化通过不等于所有使用体验已验收。

**拟定：**密码条目可增加备注、来源、上次成功时间及使用计数；如加入这些字段，应先设计兼容迁移和存储安全，不直接假定已实现。

## 5. 解压/解密与格式扩展

- 保留并增强“真实文件头/结构验证 → 安全计划 → 有限密码恢复 → 递归解压 → 内容根识别 → 交付”流程。
- 不把“7-Zip 可以尝试打开”当作本程序已经完整支持：分别列出**可识别**、**可预览**、**可解压**、**可解密**、**可递归处理**、**真实样本通过**。
- 第一组重点核对现有 ZIP、7Z、RAR/RAR5、LZ4、常见分卷系列（例如 7z.001、part01.rar、z01）在不同工具存在/缺失条件下的真实能力。
- 第二组计划验证 TAR、GZ/TGZ、BZ2/TBZ2、XZ/TXZ、Zstandard/ZST 及其组合包装；优先补强可安全识别、可列目录、可测试的路径。
- ISO、CAB、WIM 等列入**评估候选**；不能仅按扩展名宣称支持，也不能无视镜像/容器自身语义。
- 分卷缺失、损坏、密码错误、文件伪装、未知格式与工具缺失要提供不同错误说明。
- 保存 APK、Office 文件、EPUB、JAR 及游戏内部存档等内容容器的现有默认保护策略；只有明确意图或可验证的包装层才进一步解包。
- 每新增格式必须含正例、误识别反例、损坏/加密例（适用时）、路径与资源限制、安全回归；不得降低 CRC、SHA-256、路径边界或输出配额检查。

## 6. 一键压缩与加密（新增模块，未实现）

- 能选择单个/多个文件、目录，创建新归档；可设置格式、压缩等级、输出目录和文件名。
- 优先支持 ZIP、7Z 创建，并根据实际工具提供的算法暴露加密选项；例如 7Z 的 AES-256。加密选项不能暗示所有 ZIP 实现都有同等强度。
- 支持手工设置与确认密码、按用户授权从密码库选择密码；默认遮盖，不能在日志、history 或完整命令行中输出密码。
- 目标路径冲突时不覆盖旧压缩包；写入应尽可能用临时目标和成功后提交，失败留下可理解的报告，不破坏源文件。
- 完成后进行真实的结构测试/完整性验证，必要时验证密码可用；不能单凭进程退出 0 就宣称成功。
- 用户能分辨“无密码压缩”“已加密压缩”“只加密部分内容或文件名是否可见”的不同结果。
- 分卷、批量任务、压缩预设、拖放和其他输出格式为下一步增量目标；RAR 创建仅在相应正版工具能力及许可条件满足时考虑。
- 压缩与加密模块应复用现有安全/路径/工具管理能力，不把压缩输出误交给“解压后自动清理”逻辑。

## 7. 不可破坏的安全底线

1. 不修改、覆盖或删除源压缩包和用户原始目录。
2. 不覆盖既有 GameArchive_Output 或新创建的压缩文件；发生同名冲突需安全处理。
3. 不因文件名相同就去重；不因文件夹名像临时目录就删除。
4. 不降低 CRC、SHA-256、强关系验证、路径穿越检查、符号链接/reparse point 防护和配额。
5. 不静默下载/安装工具，不使用未知来源二进制，不要求用户提供账号密码。
6. 不在未授权时 push、merge、tag、发布 EXE/Release 或替换既有安装包。
7. 每次任务单人/单代理负责同一批文件写入；保留仓库现存未追踪资料及其他人的工作。

## 8. 分阶段实施与交付门槛

- **阶段 0｜需求与基线（当前）**：本文件落地；核对旧功能、真实格式能力与 UI 差距；不改现有版本身份。
- **阶段 1｜密码库可靠性**：先做最小安全存储修复（原子保存、损坏错误、兼容性、测试），再完成可用的独立管理 UI；通过重启和实际手工使用验收。
- **阶段 2｜UI 设计与实现**：先给导航与核心任务流程可视化方案，再分页面实现；进行中英双语言、两主题/自动模式、窗口尺寸与高 DPI 真机截图验收。
- **阶段 3｜格式能力扩充**：做真实能力矩阵，选择可验证的常用格式逐项实现，逐格式留下正负样本证据。
- **阶段 4｜压缩加密**：先 ZIP/7Z 的新建、加密与校验，再逐步支持分卷、更多格式和预设。
- **阶段 5｜回归与交付**：针对性测试 → 全套自动化 → 真实样本 → 必要的干净 Windows VM → 用户确认后再决定发布，不提前宣称 EXE 可用。

每个阶段都要留下：修改文件、具体功能、测试命令/实际结果、未验证风险、界面截图或真实样本证据，以及下一阶段入口。阶段之间可根据真实问题调整顺序，但不得把规划写成完成。
